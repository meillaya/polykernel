# PolyKernel Performance Model + Projections

> **Real vs projected.** The **RTX 6000 Ada (sm_89) speedups in the benchmark reports are
> MEASURED** on the pod with CUDA events: unfused 1.000× / fused 0.838× / autotuned
> 0.857× (`reports/ada6000_bench.json`; the pod story is in the "Getting REAL numbers"
> section below). The H100/A100/MI300 speedups are **PROJECTED, NOT MEASURED**: no
> NVIDIA rental was provisioned; they are derived from a compile-time **roofline model**
> + analytic memory traffic, not from a rented-GPU run. Every projected figure carries
> its status (`status: "PROJECTED"`, `projected: true`, `measured: false` in the bench
> JSONs; the `scored_by` tuning-cache field distinguishes `compile-time-model` from
> `real-benchmark`). **No SOTA-performance claim is made**: the goal is the
> compiler/runtime machinery, not beating vLLM.

## The roofline model

`lib/Analysis/Roofline.cpp` models each op's wall time as the slower of its compute and
memory bounds, divided by an attainment factor:

```
t       = max(flops / peak_flop, bytes / peak_bw) / eta
speedup = t_unfused / t_variant
```

Per-op traffic is **analytic** (from tensor shapes + dtype, the Todo 17 model):

```
bytes = (M·K + K·N + M·N) · dtype_bytes        # read A[M,K] + B[K,N], write C[M,N]
flops = 2·M·N·K
AI    = flops / bytes                            # arithmetic intensity (flop/byte)
```

An op is **compute-bound** if `AI > ridge` (the roofline ridge point), else
**memory-bound**. The ridge point is `peak_flop / peak_bw`:

| arch | peak TFLOPS | peak BW (GB/s) | ridge (flop/byte) |
|---|---|---|---|
| NVIDIA H100 (SXM5, sm_90) | 989 | 3350 | 295.2 |
| NVIDIA A100 (80GB, sm_80) | 312 | 1555 | 200.6 |
| NVIDIA RTX 6000 Ada (sm_89) | 91.1 | 960 | 94.9 |
| AMD Instinct MI300X (gfx942) | 1307.4 | 5300 | 246.7 |

**Roofline-convention note (load-bearing, do not conflate):** the H100/A100
**989/312 TFLOPS entries are the TENSOR-core dense-FP16 rates**, whereas the sm_89
**91.1 TFLOPS is the SCALAR bf16 rate** (per the CUDA C++ BPG "native arithmetic
throughput" table: sm_89 bf16 = 128 results/clk/SM = 1× FP32; fp16-half2 ≈ 182 and
tensor-core dense FP16 ≈ 364.25 are the tensor rates). This project's portable **scalar**
kernels run their FMAs on the FP32 pipes, so the sm_89 entry is the honest comparison
point for them; the H100/A100 tensor rates are a different convention and must not be
compared against 91.1 directly. The datasheet's 1457 (FP8-with-sparsity) is never used
raw. (Sources: `lib/Analysis/Roofline.cpp` + `roofline_test.cpp`.)

**Attainment assumptions (documented modeling knobs, not measured efficiencies):**
scalar GEMM `η = 0.12`, autotuned vectorized/WMMA `η = 0.35`, elementwise `η = 0.8`. These
are the only free parameters; they are stated explicitly so the projection is reproducible
and honestly labeled.

## The projected speedups (unfused = 1.00× baseline)

Fragment: `MLP block (examples/mlp_block.mlir): rmsnorm+matmul+gelu+matmul+add`, bf16,
M=2048, K=4096, N_up=11008, N_dn=4096. Source: `reports/h100_bench.json`,
`reports/mi300_bench.json` (generated by `benchmarks/run_bench_suite.py`).

| arch | backend | unfused | fused | autotuned |
|---|---|---|---|---|
| NVIDIA H100 (SXM5, sm_90) | cuda (sm_90) | 1.000× | 1.004× | **2.838×** |
| NVIDIA A100 (80GB, sm_80) | cuda (sm_80) | 1.000× | 1.003× | **2.862×** |
| AMD Instinct MI300X (gfx942) | hip (gfx942) | 1.000× | 1.003× | **2.850×** |

Projected fragment wall time (ms):

| arch | unfused | fused | autotuned |
|---|---|---|---|
| H100 (sm_90) | 3.1772 | 3.1647 | 1.1195 |
| A100 (sm_80) | 10.0055 | 9.9785 | 3.4954 |
| MI300X (gfx942) | 2.3954 | 2.3875 | 0.8403 |

### Reading the numbers

The fragment is **compute-bound** — the two matmuls have AI ≈ 1215 flop/byte, far above
every ridge point. So fusion's traffic elimination projects only a **modest** speedup
(~1.004×); the **headline gain is the scalar → autotuned attainment jump** (η 0.12 → 0.35),
i.e. the difference between the naive scalar GEMM and the bounded-grid vectorized/WMMA
config the autotuner selects. The per-op roofline (in the bench JSONs / the
`h100_report.html` / `mi300_report.html` detail pages) shows the two matmuls dominating
the wall time and the elementwise ops (rmsnorm/gelu/add) being memory-bound and tiny.

## Two distinct traffic-reduction metrics (do not conflate)

| Metric | Wave | Source | Reduction |
|---|---|---|---|
| **GPU global-memory traffic** | 3 (Todo 17) | `reports/mlp_traffic.json` | 33,554,432 B (32 MiB) = **7.02%** of fragment traffic |
| **Dataflow fabric wavelets** | 7 (Todo 38) | `reports/dataflow_metrics.json` | **99.99%** (the eliminated intermediate crosses the fabric as zero wavelets) |

Different schemas, different reports. The GPU metric is the whole-pipeline global-byte
view; the dataflow metric is the eliminated intermediate's fabric wavelets vs the matmul
broadcast. Both stem from the same fusion (`fused_rmsnorm_matmul` eliminating
`tensor<1x2048x4096xbf16>`).

## Caveats (carried verbatim into the reports)

- **MEASURED for the RTX 6000 Ada (sm_89), PROJECTED for H100/A100/MI300**: the sm_89
  numbers are real CUDA-event timings on the pod; H100/A100/MI300 come from the roofline
  model + analytic traffic, not a rented-GPU run.
- The **attainment factors are documented modeling assumptions**, not measured efficiencies.
- The generated **fused kernel recomputes the per-row RMS in every output tile**, so the
  *real* fusion speedup is shape-dependent: confirmed by the measured Ada run, where the
  fused kernel is *slower* (0.838×) at this compute-bound shape (AI ≈ 1215 >> ridge),
  matching the verified gfx1101 behavior at small, compute-light shapes.
- The CUDA tensor-core path (`matmul_mma.cu`) and the runtime launcher
  (`cuda_run_main.cpp`) are **built + compile-validated locally** (sm_80/89/90) and
  **runtime-validated on the RTX 6000 Ada (sm_89) pod**: 0 failed correctness (18/18
  golden, `reports/pass2_ada_cuda_run.log`; see
  [`cuda_backend.md`](cuda_backend.md)).

## Getting REAL numbers (opt-in, owner-gated)

The **RTX 6000 Ada (sm_89) pod has run the real validation** (this is the measured source
of the numbers above): the CUDA runtime-validation harness
(`lib/Runtime/cuda_run_main.cpp` + `tests/kernels/test_mma.py`) ran the correctness-gated
launches on the actual GPU with 0 failed correctness (`reports/pass2_ada_cuda_run.log`,
`reports/pass2_ada_mma.log`), and `benchmarks/bench_cuda.cpp --arch sm_89` produced the
MEASURED speedups (`reports/ada6000_bench.json`). The original pod (65.109.75.15) was
terminated by the user; a new RTX 6000 Ada pod (216.81.200.13, user ubuntu) was provisioned
at the user's authorization and is the one that ran the validation (`reports/pod_env_v2.log`
GATE VERDICT: PASS).

The H100/A100/MI300 real runs remain the opt-in RunPod rental:

```bash
export RUNPOD_API_KEY=<your-key>          # ~$50-100 ceiling, enforced by the script
./benchmarks/rent_runpod.sh --suite mlp   # provisions H100/A100 + MI300, runs the
                                          # correctness-gated bench, writes REAL numbers
```

With credentials, the suite overwrites `reports/{h100,mi300}_bench.{json,md}` with
**measured** unfused/fused/autotuned speedups (and flips `measured: true`). Without
credentials it exits **SKIPPED** (not FAILED) and leaves the clearly-labeled projections in
place (`reports/w5_rent_skipped.log`). The benchmark dashboard
(`tools/polykernel-report/dashboard.py --dashboard`) carries the real-vs-projected label
through automatically from the bench JSON status.
